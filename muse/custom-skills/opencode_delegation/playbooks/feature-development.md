# Feature development

1. For feature development, give OpenCode `plan` the user's goal, relevant findings and decisions, and any repository named in the request or conversation. Ask it to use `plan-feature` to decide where the work belongs. If it returns an unresolved choice between an existing and a new repository, relay that one question. Relay other planning questions and the proposed plan as they come up. Carry the user's answers back into the same planning session.
2. Forward the user's approval and the relevant plan to a write-capable OpenCode run for the requested action. For a new repository, relay the proposed setup and wait for explicit approval of that setup before delegating `init-project`. OpenCode records agreed ADRs in the target repo and uses `manage-project-issues` to manage GitHub Issues and Projects. Use the configured non-interactive `build-auto` route when the existing connection cannot handle interactive approvals. Pass the exact authorized operation and destination.
3. Keep the original `plan` session ID during setup. Ask the `init-project` run to return the absolute checkout path on the OpenCode host, then send that path to the original `plan` session. Ask it to move itself and continue the new-project workflow in `plan-feature`. If a follow-up is needed after the move, use the same session ID. Use a fresh `plan` session in the checkout if the original session cannot resume or reports that the move failed.
4. For a direct Issue or Project request, route it straight to OpenCode with `manage-project-issues` in a mode with `gh` access. Include the Issue or Project identifier and the requested operation. Relay the returned links, status, and any decision still needed in the original Muse thread.

The user can continue design or manage Issues directly in OpenCode. GitHub Project states are the handoff to herdr-symphony for implementation, independent PR verification, and merge after user approval.

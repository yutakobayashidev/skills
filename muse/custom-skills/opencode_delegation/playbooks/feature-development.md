# Feature development

1. For feature development, give OpenCode `plan` the user's goal, relevant findings and decisions, and any repository named in the request or conversation. Ask it to use `plan-feature` to decide where the work belongs. If it returns an unresolved choice between an existing and a new repository, relay that one question. Relay other planning questions and the proposed plan as they come up. Carry the user's answers back into the same planning session.
2. Forward the user's approval and the relevant plan to a write-capable OpenCode run for the requested action. For a new repository, relay the proposed setup and wait for explicit approval of that setup before delegating `init-project`. OpenCode records agreed ADRs in the target repo and uses `manage-project-issues` to manage GitHub Issues and Projects. Use the configured non-interactive `build-auto` route when the existing connection cannot handle interactive approvals. Pass the exact authorized operation and destination.
3. Keep the original `plan` session ID during setup. Ask the `init-project` run to return the absolute checkout path on the OpenCode host, then send that path to the original `plan` session. Ask it to move itself and continue the new-project workflow in `plan-feature`. If a follow-up is needed after the move, use the same session ID. If the original session cannot resume or the move fails for any reason, including a denied `external_directory` permission, start a fresh `plan` session in the checkout and give it the original session ID. Ask it to read that session with `handoff_read`, `context` mode first, then `messages` for the user's decisions and constraints, and continue the new-project workflow there.
4. Before asking OpenCode for the decomposition, confirm the release scope, expected behavior, and acceptance criteria through `plan-feature`. Relay any unresolved requirements or implementation prerequisites to the user and bring the answers back to the same `plan` session. If a decision needs an experiment, keep the affected behavior in planning until the result supports a decision or the user defers that behavior. Ask OpenCode to carry forward decisions already agreed and to record the accepted requirements and any needed ADR before publication.
5. Treat the published decomposition as the end state of planning. Check that the draft covers every undelivered part of the agreed scope, grouped under an Epic when there are several. Check that `Blocked by` links order delivery work and that the batch has no unresolved decisions or required experiments in its dependency graph. Return incomplete drafts to the `plan` session. Relay the full decomposition as one approval question and wait for the user's answer. After approval, delegate one `manage-project-issues` run to publish the approved Issues, link Epics and implementation prerequisites, and add the implementation Issues as `Todo` to the account-level [Agent Work Queue](https://github.com/users/yutakobayashidev/projects/3), shared by every repository. Relay the Issue and Project links. Moving Issues to `Implement` requires a separate approval, which can cover several Issues. Symphony uses the `Blocked by` graph to wait for earlier implementation work.
6. For a direct Issue or Project request, route it straight to OpenCode with `manage-project-issues` in a mode with `gh` access. Include the Issue or Project identifier and the requested operation. Relay the returned links, status, and any decision still needed in the original Muse thread.

The user can continue design or manage Issues directly in OpenCode. From `Todo` onward, GitHub Project states hand the work to herdr-symphony for implementation, independent PR verification, and merge after user approval.
